# PatchPilot AI — Product Requirements Document

**Version:** 1.0  
**Status:** MVP specification  
**Project:** REFORGED ’26 Hackathon  
**Product category:** Agentic developer tooling

## 1. Product overview

PatchPilot AI is a regression-aware code repair verification system that evaluates AI-generated code patches through deterministic validation, controlled test execution, and baseline-versus-patched result comparison.

PatchPilot is not intended to replace general-purpose coding agents. It aims to provide a consistent verification workflow for patches proposed by tools such as OpenCode and other supported AI coding agents.

**Product principle:** AI proposes a fix; evidence determines its verification status.

## 2. Problem statement

AI coding agents can analyze source code, generate patches, and execute tests. However, a proposed fix may:

- Fail to resolve the original bug.
- Introduce regressions in previously working functionality.
- Modify files outside the intended scope.
- Pass a limited test suite while leaving other defects undiscovered.
- Produce explanations that are not supported by actual execution results.

Developers need a transparent way to evaluate proposed changes and understand the evidence behind the outcome.

## 3. Product vision

Build a lightweight, agent-independent verification layer that accepts a proposed patch, evaluates its safety and test outcomes, and produces an inspectable report.

The system must distinguish between a patch being syntactically valid, tests passing, and the broader software being correct. These are different claims.

## 4. Target users

### Primary users
- Developers using AI coding assistants.
- Student developers and hackathon teams.
- Small engineering teams reviewing AI-generated patches.

### Secondary users
- Open-source maintainers.
- Teams evaluating multiple coding agents.
- Engineering educators demonstrating software testing and regression detection.

## 5. MVP goals

The first MVP must demonstrate a complete, reproducible workflow:

1. Accept a bug description and a supported sample project.
2. Generate or import a proposed code patch.
3. Validate patch format and permitted file paths.
4. Run the same predefined test suite against baseline and patched versions.
5. Compare actual outcomes.
6. Identify resolved failures and newly failing tests.
7. Produce an evidence-backed verification report.
8. Allow a developer to inspect the patch, logs, and limitations.

The MVP should demonstrate at least one successful repair and one regression scenario.

## 6. Non-goals

The initial MVP will not:

- Replace OpenCode, Claude Code, Cursor, or other coding agents.
- Guarantee that a patch is correct or bug-free.
- Automatically merge or push code to a remote repository.
- Execute arbitrary commands generated by an AI model.
- Support every programming language or build system.
- Autonomously modify production systems.
- Claim comprehensive security verification.
- Require a multi-agent architecture when a simpler workflow is sufficient.

## 7. Core user workflow

### Step 1: Submit
The user selects a supported sample project and provides a bug description or proposed patch.

### Step 2: Analyze
If a patch has not been supplied, the system may use Google Gemini API to analyze the relevant source and propose a structured patch.

### Step 3: Validate
The backend checks the patch format, target paths, allowed file scope, and configured size limits. Invalid patches are rejected before application.

### Step 4: Establish baseline
The system creates a disposable copy of the original project and runs the predefined test suite. Baseline results must be captured before comparing the patched version.

### Step 5: Apply and test
The validated patch is applied to a separate disposable workspace. The same predefined tests run with the same configuration.

### Step 6: Compare
The system compares test identities and outcomes, including resolved original failures, newly failing tests, and execution errors.

### Step 7: Report
The dashboard displays the patch, test summaries, relevant logs, final classification, and limitations.

## 8. Functional requirements

### FR-01: Bug and patch input
- Accept a bounded bug description.
- Support a predefined local sample project in the first release.
- Allow a proposed patch to be supplied or generated.
- Reject unsupported or oversized inputs with clear errors.

### FR-02: AI patch proposal
- Use the official Google Gen AI Python SDK.
- Read the API key from server-side environment configuration.
- Return structured output: summary, likely root cause, evidence, proposed diff, suggested tests, and limitations.
- Treat source code and repository text as untrusted input.
- Never treat a model's explanation as proof that a fix works.

### FR-03: Patch validation
- Parse and validate unified diffs.
- Reject malformed patches.
- Reject absolute paths and path traversal.
- Restrict edits to explicitly permitted source files.
- Reject prohibited file changes.
- Apply patches only to disposable copies.
- Do not push changes or modify the original project.

### FR-04: Test execution
- Use predefined test commands for supported sample projects.
- Run baseline and patched versions under comparable conditions.
- Capture exit status, logs, test identities, pass/fail outcomes, and duration where available.
- Distinguish ordinary test failures from runner errors, timeouts, and incomplete runs.
- Use disposable isolated execution with restricted permissions, resource limits, and disabled network access.
- Do not execute arbitrary model-generated shell commands.

### FR-05: Verification classification
The comparison engine must support these outcomes:

- `IMPROVED`: one or more baseline failures are resolved and no new failures are observed among comparable tests.
- `REGRESSION_DETECTED`: at least one previously passing test now fails.
- `PARTIAL_FIX`: some baseline failures are resolved, but failures remain.
- `NO_IMPROVEMENT`: the available comparable results show no meaningful improvement.
- `INCONCLUSIVE`: execution errors, timeouts, missing baseline results, or incomparable test outcomes prevent a reliable conclusion.

A regression takes precedence over a positive improvement classification when both occur. Incomplete execution must not be classified as success.

### FR-06: Results dashboard
Display:
- Bug description and proposed root cause.
- Patch preview.
- Patch validation status.
- Baseline and patched test summaries.
- Resolved failures.
- Newly failing tests.
- Execution errors and logs.
- Verification classification.
- Explicit limitations.

### FR-07: Workflow orchestration
n8n may coordinate workflow steps and notifications after the core backend works. Core validation and classification must remain testable independently of n8n.

## 9. Non-functional requirements

### Security
- Keep API keys on the backend.
- Do not expose host credentials to test containers.
- Do not mount the Docker socket into untrusted test environments.
- Apply path validation and input limits.
- Use restricted execution environments.
- Never automatically accept, merge, or push a patch.

### Reliability
- Capture actual test results rather than inferred results.
- Handle missing dependencies, model failures, timeouts, and runner errors explicitly.
- Make repeated comparisons reproducible where the environment permits.
- Preserve logs needed to explain the reported outcome.

### Maintainability
- Separate API routes, schemas, AI integration, patch validation, test execution, comparison logic, and reporting.
- Use typed interfaces and automated tests.
- Keep comparison logic deterministic and independent of the AI provider.

### Usability
- Use clear status labels and readable diffs.
- Explain why a patch was rejected or classified as a regression.
- Avoid unsupported claims such as "bug-free" or "guaranteed correct."

## 10. Suggested architecture

- Frontend: React, TypeScript, Vite, Tailwind CSS.
- Backend: Python, FastAPI, Pydantic.
- AI: Google Gemini API through the official Google Gen AI SDK.
- Repository access: local sample projects initially; GitHub REST API later.
- Patch processing: validated unified-diff workflow.
- Tests: pytest.
- Isolation: Docker with restricted resources and network access disabled.
- Orchestration: n8n as an optional later integration.

## 11. MVP acceptance criteria

The MVP is demonstrable when:

1. The backend starts and its health endpoint responds.
2. Automated tests validate every comparison classification.
3. A reproducible baseline bug has a real failing test.
4. A valid patch can be validated and applied to a disposable copy.
5. Baseline and patched tests run with the same configured test suite.
6. A successful repair scenario is classified using actual results.
7. A regression scenario is identified using actual newly failing tests.
8. Invalid patches are rejected before execution.
9. Runner errors and timeouts are not reported as successful verification.
10. The frontend displays actual patch and test evidence.
11. The README explains setup, the demo, supported scope, and limitations.
12. No unimplemented capability is represented as complete.

## 12. Evaluation plan

Use reproducible sample bugs and record:

- Whether the patch applies successfully.
- Whether original failing tests pass after the patch.
- Number of newly failing tests.
- Whether execution completed reliably.
- Whether the classification matches the recorded outcomes.
- End-to-end execution time, where measured.

Do not publish accuracy, success-rate, cost, or performance claims until the evaluation has actually been run and documented.

## 13. Risks and limitations

- Incomplete test coverage can hide regressions.
- Nondeterministic tests can make comparisons unreliable.
- A passing test suite does not prove full correctness.
- Environment differences can affect results.
- AI-generated patches can be unsafe or irrelevant.
- Arbitrary repositories may require unsupported runtimes or dependencies.

The system must report these limitations rather than conceal them.

## 14. Delivery priorities

### P0 — Required for MVP
Backend foundation, deterministic comparison engine, reproducible sample bugs, patch validation, actual test execution, and verification report.

### P1 — Required for a strong demo
Gemini integration, clean dashboard, successful repair scenario, regression scenario, and clear logs.

### P2 — After core validation works
GitHub integration, n8n orchestration, support for additional project types, and broader benchmark evaluation.

## 15. Definition of done

A feature is complete only when its acceptance criteria are implemented, relevant automated tests pass, the actual behavior has been verified, and its limitations are documented.

A generated code file or a successful frontend build alone is not sufficient evidence that the complete workflow works.
